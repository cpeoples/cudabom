# Changelog

All notable changes to this project are documented here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project
adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Symbol-set identity for large static archives.** The big `.a` aggregates
  (`libnccl_static.a`, `libcutensor_static.a`, `libcudss_static.a`, …) whose
  member hashes do not survive static linking, and were therefore skipped
  entirely, now contribute a **symbol-marker** fingerprint: the component's
  namespaced public-API symbols (e.g. `nccl*`, `cutensor*`), derived from the
  members' `.symtab` and recorded in the fingerprint DB (new `symbol_markers`
  field, schema v3). On scan, an object exporting at least two of a component's
  marker symbols is named at **`Likely`** confidence (never `Exact`: a symbol
  set identifies the component, not a version) with `exported-symbol-set`
  evidence. This closes the one capability gap where a general binary tool could
  name a static CUDA archive that cudabom skipped, without inventing any
  fingerprint; the symbols are first-party and namespaced.


- **Full binary-layer coverage across every lock-backed CUDA toolkit release
  (11.4.2 → 13.4.2).** Backfilled all 50 previously manifest-only CUDA shards to
  carry inner-`.so` build-ids and hashes (55/64 total shards now enriched,
  including the cuDNN/cuTENSOR/NCCL/cuDSS families). The database holds 2,266
  build-ids (1,138 distinct) with **zero cross-component collisions**; 167
  build-ids are legitimately shared across multiple versions of the same library
  (worst: one `curand` build-id spans 23 releases), which the new
  `candidate_versions` reporting makes explicit.

- **cuDNN 9.0.0.312 fingerprints (manifest + binary layer).** Added the
  first-party `redistrib_9.0.0.json` manifest (fetched from NVIDIA's cuDNN redist
  index, SHA-256-verified) and derived the inner-`.so` build-ids/hashes from the
  9.0.0.312 cuda11/cuda12 archives. The `nvidia-cudnn-cu12 9.0.0.312` wheel now
  resolves to **exact `9.0.0.312`** (previously a `9.x` family) and correlates 28
  CVEs. Note: NCCL `2.27.7` cannot be enriched the same way: NVIDIA's NCCL redist
  index only publishes back to `2.29.2`, so no first-party manifest exists for
  `2.27.7` and cudabom does not invent fingerprints; that wheel stays family-level.

- **Corpus locks for the cuDNN, NCCL, and cuTENSOR families.** The nightly
  `fingerprints backfill` resolves each shard's archives from
  `fingerprints/corpus.<label>.lock.json`; the family shards had no such lock, so
  a future family release could never be auto-enriched (it would stay a `x`
  family with no CVE correlation). Generated and committed
  `corpus.9.0.0.lock.json`, `corpus.9.27.0.lock.json`,
  `corpus.2.32.3-cuda12.9.lock.json`, and `corpus.2.8.1.lock.json` (full URLs +
  NVIDIA SHA-256, per platform/CUDA variant). Verified end-to-end that fetching
  cuTENSOR 2.8.1.0 through its new lock and re-deriving reproduces the committed
  shard's build-ids **byte-for-byte**, so family backfill is now as safe and
  reproducible as the CUDA-toolkit path.

- **Documentation site** (Hugo + the Relearn theme): the long-form docs plus
  data-driven reference pages: CUDA coverage (from the fingerprint database),
  advisory coverage (from the advisory index), and a CLI reference (from
  `cudabom --help`), are generated by `.hugo/scripts/build_docs.py` from the
  repo's own docs and data, then built and deployed to GitHub Pages by
  `.github/workflows/docs.yml`. The Relearn theme is vendored as a git
  submodule under `.hugo/themes`. Preview locally with
  `python .hugo/scripts/build_docs.py && hugo server -s .hugo`.
- **`cargo xtask eval`**: a measured, reproducible comparison harness that runs
  cudabom and (when installed) OWASP blint, Syft, and Trivy through their own
  CLIs on the same real artifacts and records, per tool, whether each **names**
  a CUDA component, **pins the exact version**, and **correlates a CVE**. A tool
  that is not installed is recorded as not-installed, never a win. With
  `--write-comparison` it splices the measured table into `docs/comparison.md`.
  On a real `libcudart.so.12` from the official `nvidia-cuda-runtime-cu12`
  wheel, cudabom pins the exact CUDA version and correlates its toolkit CVEs;
  blint surfaces the soname but pins no version and no CVE; Syft and Trivy report
  nothing for the bare shared object.

- Readable, severity-first advisory output: the `scan` table now leads with a
  severity breakdown (`N affected (X high, Y medium, Z low)`) and a `most severe`
  headline, then lists affected advisories **grouped by severity (highest first)**,
  one compact line each (id, CVSS, date, and a single canonical NVD link) sorted
  by CVSS within each group. This replaces the flat three-lines-per-CVE wall that
  made a result hard to triage. `-v` restores the full per-advisory detail
  (verdict, justification, all reference URLs). JSON/SBOM/SARIF are unchanged.
- Findings-first `scan` table: by default the file listing now shows only files
  that carry a CUDA signal (ELF, GPU code, archives, parse errors) and collapses
  uninteresting leaves (source headers, package metadata) into a single
  `... and N other file(s)` line, so a real wheel's report leads with the matched
  binary and advisories instead of a wall of header paths. `--all-files` restores
  the full per-file listing. Only affects `--format table`; JSON/SBOM/SARIF are
  unchanged and still enumerate every file.
- Advisory **reference links**: every advisory now carries reference URLs: the
  canonical NVD page for its CVE id plus any URLs from NVIDIA's CSAF, rendered
  in all report formats: the `scan` table (`references:` line), native JSON (a
  `references` array), SARIF (result `helpUri` and `properties.references`), and
  the Markdown report (host-labeled links). The vendored `advisories/index.json`
  gains these additively (schema unchanged; the field is omitted when empty), so
  a scan result links straight to each CVE instead of only naming it.
- `scan` advisory summary: the advisory section now leads with a verdict tally
  (`N affected, M not affected, K under investigation`) and, when matches exist
  but none are affected, says so explicitly; so a clean result reads as a
  deliberate verdict rather than an empty section. The `summary` object is also
  present in JSON output.
- `scan --fail-on <none|found|affected>`: choose when `scan` returns a non-zero
  exit code. Defaults to `none`.

- Full fingerprint coverage of the CUDA redistributable line: the vendored
  database now carries a derived shard for every release NVIDIA publishes at its
  redist directory index (59 releases, 11.0.3 through 13.4.2), built from the
  official archives with each download verified against NVIDIA's own SHA-256.
  Rich releases record real per-file hashes and GNU build-ids; management-only
  early releases are recorded as empty shards so discovery does not reprocess
  them. Kept current autonomously by `corpus discover` + `fingerprint-refresh`.

- Unified verbosity: a single global `-v/--verbose` (repeatable, `-vv` for
  debug) and `-q/--quiet` control diagnostic output across every `cudabom`
  subcommand and every `cargo xtask` task. Machine-readable output on stdout is
  never affected. A routine `scan` now prints a one-line summary instead of a
  flood of per-signal lines; `-v` restores the detail.
- Progress reporting: `corpus fetch` prints `[n/total]` counters and
  `fingerprints build` reports per-shard `[n/total]` status plus per-archive
  detail under `-v`, so long-running derivations show steady progress.
- `cargo xtask corpus discover`: enumerate the CUDA redist manifests NVIDIA
  actually publishes (read first-party from NVIDIA's auto-generated redist
  directory index, no hardcoded version list), diff them against the committed
  shards, and lock any new releases. `--json` emits the discovery plan for CI;
  `--limit N` bounds a batch; `--dry-run` plans without writing.
- `.github/workflows/fingerprint-refresh.yml`: nightly automation that discovers
  a bounded batch of new CUDA releases, downloads and verifies their archives,
  derives shards in parallel, reclaims the (large, gitignored) corpus from the
  runner afterward, and opens a review PR when shards change. This mirrors
  `advisory-refresh.yml`, giving the fingerprint database the same first-party,
  reviewed autonomy the advisory index already had.
- Parallel fingerprint derivation: `fingerprints build --jobs N` derives
  archives across a bounded worker pool (default 4, capped at core count),
  keeping peak memory and disk bounded. Roughly 3x faster on a multi-release
  corpus. Extraction now uses self-cleaning scratch directories, fixing a leak
  where extracted trees accumulated in the system temp directory across runs.
- **`fingerprints backfill` + a nightly workflow back-fill the binary layer into
  older shards, safely.** The nightly `fingerprint-refresh` only enriches
  *newly discovered* releases, so shards committed before binary-layer
  derivation stayed manifest-only (a wheel's library resolved to a `x` family,
  no CVE correlation), and a blanket `fingerprints build --force` would *regress*
  them (rewriting them manifest-only without their corpus on disk). The new
  `cargo xtask fingerprints backfill` finds a bounded batch of manifest-only
  committed shards, fetches **only** those releases' archives, re-derives **only**
  those shards (staging each manifest alone so the recursive builder cannot touch
  the others), and reclaims between each, so coverage compounds a few releases
  per night with no risk of regressing a shard it did not fetch corpus for. A
  `fingerprint-backfill.yml` workflow runs it nightly and opens a review PR.
- **`corpus fetch` gained `--component` and `--platform` filters.** Enriching one
  library no longer requires downloading a whole toolkit: `corpus fetch --lock
  <release> --component cublas --platform linux-x86_64` pulls just that archive.
  Both `backfill` and targeted local enrichment rely on this to stay cheap.
- **Binary-layer fingerprints for the CUDA 12.9.x math libraries, cuBLAS 13.4.1.3,
  cuDNN 9.27.0.42, cuTENSOR 2.8.1.0, NCCL 2.32.3, and cudart 11.8.89 / 12.4.127.**
  These shards now carry inner-`.so` SHA-256 hashes and GNU build-ids (derived by
  unpacking the first-party redist archives), not just the outer archive hashes.
  A PyPI wheel bundling e.g. `libcublas.so.12` is identified as `cublas 12.9.2.10
  (exact)` straight from the binary and correlates its toolkit-release advisories
  (verified: cuBLAS 12.9.2 → 33 CVEs, cuDNN 9.27.0.42 → 28, NCCL 2.32.3 → 46,
  cuTENSOR 2.8.1.0 → 28, all `via_toolkit_release`), where before it degraded to
  a `x` family with no CVE correlation. Every recorded hash/build-id maps to
  exactly one version, with no cross-version or cross-shard ambiguity.
- **The in-the-wild distribution eval is now CI-runnable, sized to GitHub's disk limits.**
  `eval --distribution` gained `--tier a|b`, `--kind <list>`, and `--stream`: tier A is
  the always-safe wheels/conda/synthetic subset (a few GB peak, fits the 14 GB
  guaranteed free space on a standard hosted runner), tier B is the full set
  including fat ML container images (PyTorch ~9 GB, TensorFlow ~6 GB extracted).
  In `--stream` mode each artifact's working set (the download, the unpacked
  tree, and, for containers, the pulled image via `docker rmi`) is reclaimed as
  soon as it is scored, so peak disk is one artifact (~9 GB) rather than the sum
  (~18-20 GB). The exported container tar is also deleted the instant it is
  extracted, roughly halving a fat image's peak. A new `distribution-eval.yml` workflow
  runs tier A nightly/on-dispatch and tier B nightly with streaming + a disk
  free-up step, uploading the eval JSON as an artifact.
- **In-the-wild CUDA wheels are now discovered automatically from PyPI.**
  `cargo xtask distribution discover` crawls PyPI's JSON API for a reviewed set of
  CUDA-bearing projects: official `nvidia-*-cuXX` wheels (cudart, cuDNN, NCCL,
  cuBLAS, cuFFT, cuRAND, cuSOLVER, cuSPARSE, nvRTC, cuTENSOR) plus third-party
  frameworks that bundle CUDA (PyTorch, CuPy, JAX, TensorFlow), and proposes
  new, content-pinned (`url` + `sha256`) manifest entries. It is **metadata
  only**: file URL, size, and digest come straight from the API, so discovery is
  kilobytes and downloads no wheels; the heavy scanning stays in `eval --distribution`
  under its `--tier`/`--stream` disk controls. Pre-releases are skipped and
  official-wheel versions are mapped to their CUDA component for exact ground
  truth. `--write` appends to `eval/distribution.manifest.json`; a new `distribution-discover.yml`
  workflow runs it nightly and opens a review PR, mirroring `fingerprint-refresh`.
- **CUDA libraries hidden at a non-zero offset are now identified.** The scan
  pipeline scans unrecognized leaf files for an ELF header past offset 0 and,
  when one *fully parses*, identifies it from its own build-id/symbols,
  reported honestly as *embedded at offset N* (`embedded_elfs` in the JSON),
  never attributing the whole-file hash to a sub-slice. This closes the distribution
  eval's `embed` case: a CUDA `.so` concatenated behind a 64 KiB junk prefix
  now resolves to its exact version (verified end-to-end: `cudart 11.8.89
  (exact)` with 26 CVEs correlated) instead of being a MISS. A stray run of the
  four magic bytes is not a match, because only candidates that parse into a
  real ELF are surfaced (`cudabom-elf::find_embedded_elf`, hermetically tested
  via `object`'s ELF writer). Mirrors the existing embedded-fatbin offset scan.
- **The cudart binary layer is now committed for the 12.4.x and 11.8.x lines.**
  Enriching `fingerprints/cuda/redistrib_{12.4.1,11.8.0}.json` with the
  unpacked-`.so` build-ids and file hashes (via `xtask fingerprints build
  --corpus`) lets libraries shipped inside PyPI wheels and containers resolve to
  an **exact** version rather than a SONAME-major family; the wheels repackage
  NVIDIA's redist bytes verbatim, so they inherit the exact match for free. An
  exact version then fires CVE correlation through the existing `cuda-toolkit`
  release mapping: `cudart 12.4.127` surfaces 16 advisories (via toolkit 12.4.1)
  and `cudart 11.8.89` surfaces 26 (via 11.8.0). The remaining cuda-tree shards
  gain their binary layer incrementally through the nightly fingerprint-refresh.

### Changed

- **Strong-signal matches now surface *every* candidate version instead of
  silently reporting the lowest.** Backfilling the full math-library binary layer
  revealed that NVIDIA ships the byte-identical `.so` (one GNU build-id) across
  many patch releases: one `npp` build-id spans up to **13** versions (avg ~4.7
  across the affected libraries: npp, cublas, cufft, cufile, nvrtc, cusolver,
  cusparse, nvjpeg, curand). There are **zero cross-component collisions**, so
  *which* library is identified is never ambiguous, only the exact micro
  version. `Component` gained a `candidate_versions` field: when a build-id or
  hash maps to more than one release, `version` holds the lowest (deterministic
  representative) and `candidate_versions` holds the complete sorted set, so the
  ambiguity is explicit. Confidence stays `Exact`: the binary match *is* exact;
  only the label is shared. The file-hash path still pins a single version
  (archive hashes stay unique), so the candidate set appears only when a shared
  build-id is the sole signal (e.g. a stripped/renamed library). The `scan`
  table shows `version (+N more)`; the groundtruth eval counts a match when the
  ground-truth version is the representative *or* in the candidate set.

- **Ground-truth eval harness now measures CVE correlation head-to-head.** The
  `cargo xtask eval` summary adds a "cudabom correlates a CVE" line (binaries
  with ≥1 affected advisory, plus the total match count) next to the existing
  "Trivy correlates a CVE" line, and records per-binary `cve_matches` in
  `eval-groundtruth.json`. Over the ground-truth corpus, cudabom correlates CVEs
  on 36 of 41 binaries (877 advisory matches) versus Trivy's 0 on the same loose
  binaries, the fair comparison the harness previously could not show.

  Markdown report were reworked so a reader sees *which component/file is
  affected and why*, not a flat wall of CVE ids:
  - Advisories are now **grouped by the component they concern** (the one tied
    to the scanned file in the `composition:` section), each block headed by its
    own affected/not-affected tally.
  - Within a component, affected advisories lead and are grouped by severity
    (worst first) as **aligned columns** (CVE, CVSS, published date, one-line
    summary) in the terminal, and as a sortable table (Advisory, Verdict,
    Severity, CVSS, Published, Summary, Links) in Markdown.
  - Each advisory now carries its **description** (NVIDIA's CSAF note text, HTML
    stripped) so the CVE has human context, not just an id. Threaded through
    `Match` -> the report verdict and present in JSON.
  - The findings line now shows the **evidence value**: e.g. the matched
    SHA-256 (`KnownFileHash sha256:256e6409e4f0…`) and the file it was observed
    in, instead of a bare `1 evidence` count.
  - Blank lines now separate the findings / composition / gpu-capability /
    advisories sections, and the per-file `composition:` advisory suffix is a
    compact count (`33 affected`) rather than the full CVE-id list (which now
    lives, with detail, in the `advisories:` section).
  - `-v` adds the per-advisory match reason and full description beneath each
    row. JSON / SARIF / CycloneDX output is unchanged.

- Toolkit-advisory correlation no longer duplicates a CVE per shipping release.
  When a scanned component version shipped in more than one CUDA toolkit release
  (e.g. the same `cudart` in 12.9.1 and 12.9.2), each affecting advisory is now
  reported once, crediting all contributing releases in the justification,
  rather than once per release. This halves noisy output and corrects inflated
  `gate` violation counts on real multi-release libraries.
- `scan` exit code: `scan` is now a reporting command that exits `0` on success
  even when it identifies CUDA or finds affected advisories. Opt into a non-zero
  exit with `--fail-on found` or `--fail-on affected`; `gate` remains the path
  for full policy enforcement. Previously any positive identification exited `1`,
  which failed CI merely for finding CUDA.
- Fingerprint schema v2: `file_hashes` and `build_ids` now map a hash/build-id
  to a *set* of versions rather than a single version. NVIDIA re-ships a
  byte-identical library under multiple component versions across toolkit
  releases (relabeled, not rebuilt); recording all of them is the truthful
  claim and stops the merge from discarding versions (and from emitting spurious
  "conflict" diagnostics). The shard merge unions these sets.

- `cudabom update`: fetch the published data bundle (fingerprint database +
  advisory index) from the project's GitHub Releases into a per-user data
  directory, so a binary-only install (crates.io, Snap, release archive) obtains
  its data without cloning the repository. The bundle
  (`cudabom-data-<tag>.tar.gz`) is verified against its `.sha256` sidecar and
  unpacked with hard size limits and path-traversal rejection. Resolution order
  for the data dir: `CUDABOM_DATA_DIR`, `SNAP_USER_DATA/cudabom`,
  `XDG_DATA_HOME/cudabom`, then `~/.local/share/cudabom`. `scan`/`gate`/`vex`/
  `enrich`/`reconcile`/`explain` now default `--db` and `--advisories` to this
  directory when the flags are omitted (a directory of shards is merged), and
  `version --verbose` reports the installed bundle tag.
- `cargo xtask bundle --tag <tag>`: package the committed data
  (`fingerprints/cuda/*.json` + `advisories/index.json`) into the
  `cudabom-data-<tag>.tar.gz` release asset and its `.sha256` sidecar,
  deterministically. Wired into the release workflow, which builds, Sigstore-
  signs, and attaches the bundle to each published release.

- Advisory enrichment from CSAF: the normalized advisory index now records, per
  advisory, a `published` date (from CSAF `document.tracking.initial_release_date`),
  a human-readable `description` (from the vulnerability `notes`, preferring a
  `description`/`summary`/`general` note), and a numeric `cvss_score` (the highest
  CVSS base score across the vulnerability's `scores`). All first-party from the
  bulletin, all optional. These flow onto each advisory `Match` and are surfaced
  in `scan` output (a metadata line in the table; `severity`/`cvss_score`/
  `published` fields in JSON).

- Release dates on fingerprint shards: each shard now carries a first-party
  `release` block (`label` + `date`) copied verbatim from the redist manifest's
  `release_date` (e.g. `12.4.1` -> `2024-04-03`). There is no per-file publish
  date in the manifest, so this single per-release date is the only grounded
  date recorded (never synthesized from HTTP headers). The directory loader
  folds shard dates into a `release_dates` map, and `scan` surfaces a
  `shipped in:` annotation dating a finding by the release that shipped it.
- Incremental, content-addressed fingerprint builds: each shard records a
  `provenance` block (manifest sha256, contributing corpus archive sha256s, and
  tool version). `cargo xtask fingerprints build` compares current inputs
  against a shard's provenance and skips re-deriving an unchanged release
  (`up to date, skipped`), so a nightly refresh only re-unpacks/re-parses new or
  changed releases. `--force` rebuilds every shard regardless.
- Full-corpus fetch from a directory: `cargo xtask corpus fetch --lock <dir>`
  merges every `corpus.*.lock.json` shard in a directory (de-duplicated),
  defaulting to `fingerprints/`; a single lockfile path still works for a subset
  run. Corpus lockfiles are now consistently sharded per release
  (`corpus.<version>.lock.json`).

- Component descriptions and licenses: fingerprint shards now carry NVIDIA's own
  human-readable description (e.g. `CUDA Runtime (cudart)`) and license (`CUDA
  Toolkit`) per component, taken verbatim from the redist manifest. Surfaced in
  `scan` output (a `catalog` map in JSON; an annotation line in the table) and
  in `reconcile` (on matched and discovered-only components).

- `cudabom reconcile`: compare a declared CycloneDX SBOM/VEX (e.g. from NVIDIA
  NGC) against the CUDA components cudabom discovers in an artifact, reporting
  `matched` (with declared VEX statements attached), `declared_only`, and
  `discovered_only` (components a declaration under-reports). Comparison is by
  canonical CUDA identity, so third-party names (`cuda-cudart`, `libcublas-12-4`,
  `libcudart.so.12`, purls) line up with cudabom's canonical names. Offline by
  default via `--sbom`/`--vex`; optional key-gated NGC fetch via `--ngc-image`
  (`--ngc-api-key`/`NGC_API_KEY`).
- CycloneDX declaration reader (`cudabom_sbom::DeclaredBom`) and a declared-name
  normalizer (`cudabom_identify::canonicalize_declared_name`).
- Committed offline NGC-shaped fixtures under `fixtures/ngc/`.

- Per-node advisory verdicts on the binary composition view: each `links` and
  `contains` node now carries the advisory verdicts for its component
  (`affected`/`not_affected`/`under_investigation`), in both scan JSON and the
  table output.
- Library-version to toolkit-release correlation: fingerprint shards now record
  `release_versions` (each component version -> the CUDA toolkit release that
  shipped it, from the redist manifest's `release_label`), and `scan` uses it to
  correlate toolkit-level (`cuda-toolkit`) advisories against individually
  scanned libraries. Indirect matches are tagged `via_toolkit_release` for
  transparency and evaluated fully offline.

- Populated `advisories/index.json` from NVIDIA's real CSAF feed
  (`NVIDIA/product-security`, pinned commit) via `cudabom db update`: 74
  normalized advisory records covering `cuda-toolkit`, `tensorrt`, and `nvjpeg`.
  Scanning with `--advisories` correlates findings against this committed,
  offline snapshot.

- CSAF version parsing now recognizes NVIDIA's "Update N" and compact `U<n>`
  suffixes, mapping them to a patch component (e.g. `11.6 Update 2` -> `11.6.2`,
  `12.5U1` -> `12.5.1`), tightening affected/fixed bounds in `advisories/index.json`.

- Initial Cargo workspace scaffold: `cudabom-core` domain types
  (`Artifact`, `Location`, `Component`, `Evidence`, `Confidence`, `Finding`)
  and a tunable `Limits` safety config, plus stub crates for extraction, ELF,
  fatbin, identify, advisory, sbom, report, and policy.
- `cudabom` CLI with `version --verbose` and `schema`, documented exit codes,
  and the full command surface declared for `--help`.
- `xtask` workspace-automation binary skeleton.
- Repository standards: Apache-2.0 `LICENSE` and `NOTICE`, `SECURITY.md`,
  `CONTRIBUTING.md`, `RELEASING.md`, `CODE_OF_CONDUCT.md`, `DECISIONS.md`.
- Centralized configuration: workspace dependency/lint management, `rustfmt.toml`,
  `clippy.toml`, `deny.toml`, `rust-toolchain.toml`.
- CI and supply-chain workflows: build/lint/test, cargo-audit, CodeQL,
  OpenSSF Scorecard, Dependabot; SHA-pinned actions with hardened runners.
- Release pipeline scaffold: multi-target build matrix, SLSA Build L3
  provenance, CycloneDX SBOM, Sigstore signing, and a composite GitHub Action.
- `docs/` skeleton: architecture, evidence model, advisories, threat model,
  benchmarks, comparison, and fingerprint provenance.
- Safe extraction layer (`cudabom-extract`): in-memory, execution-free walking
  of files, directories, wheels/zips, tarballs, and gzip streams, with content
  detection by magic bytes and a shared `Budget` enforcing nesting depth,
  aggregate and per-file byte caps, decompression-ratio and entry-count limits.
  Hardened against zip-slip, absolute/Windows paths, symlink/hardlink escape,
  and decompression bombs, with a malicious-archive test suite.
- ELF fact extraction (`cudabom-elf`): panic-free parsing of class/endianness,
  object type, architecture, `DT_SONAME`, `DT_NEEDED`, run paths, GNU build-id,
  section names, exported dynamic symbols, and bounded rodata string extraction.
- GPU code inventory (`cudabom-fatbin`): bounds-checked, panic-free parsing of
  NVIDIA fatbin containers (wrapper magic, entries with kind/SM/compression) and
  PTX modules (`.version`, `.target sm_NN`, `.address_size`), plus a scan for
  fatbins embedded in ELF files.
- `cudabom scan` wired end to end (extract -> ELF facts -> GPU code ->
  identify -> SBOM) with deterministic JSON, table, and CycloneDX output.
- CUDA component identification (`cudabom-identify`): a data-driven fingerprint
  database (empty by default; no invented fingerprints), a structural
  SONAME-grammar matcher, and a confidence engine (Exact/Likely/Unknown)
  producing evidence-backed findings. Wired into `cudabom scan` via `--db`, with
  a `Findings` exit code when a component is positively identified.
- CycloneDX 1.6 SBOM emission (`cudabom-sbom`): deterministic BOM output with a
  content-derived serial number, the scanned artifact as `metadata.component`, a
  dependency graph, and cudabom facts (confidence, evidence, relationship)
  carried as namespaced properties. Emitted via `cudabom scan --format cyclonedx`.
- Advisory correlation (`cudabom-advisory`): a normalized, schema-versioned
  advisory index (JSON), a purpose-built dotted-numeric version comparator with
  consistent equality/ordering (`12.4` == `12.4.0`), and a conservative matcher
  producing VEX-style `affected` / `not_affected` / `under_investigation`
  verdicts. Exact versions resolve directly against affected/fixed ranges; a
  `Likely` major-only version (`12.x`) yields a definitive verdict only when the
  entire major series is on one side of the boundary, otherwise
  `under_investigation`; `Unknown` never yields an affected/not-affected claim.
  Wired into `cudabom scan` via `--advisories`, and every advisory result
  carries the standing caveat that absence of a match is not proof of safety.
- Reporting formats (`cudabom-report`): deterministic SARIF 2.1.0 and Markdown
  renderers. SARIF declares a stable rule per identification confidence and per
  advisory verdict, maps findings and verdicts to results with an actionability
  `level` (an `affected` advisory verdict is `error`), and attaches component,
  version, confidence, and advisory id as result properties. Markdown emits a
  findings table and an advisory table with the coverage caveat, cell-escaped
  for PR/MR comments. Wired into `cudabom scan --format sarif|markdown`, which
  were previously stubbed. The report layer stays independent of the advisory
  database by consuming a neutral verdict type.
- Policy gate (`cudabom-policy`) and the `cudabom gate` command: a tunable,
  schema-versioned JSON policy that turns a scan result into a pass/fail
  decision. Secure by default (fail on any `affected` advisory verdict);
  optional `min_confidence` and `under_investigation` failure conditions; and an
  auditable allowlist where every exemption requires a reason and is scoped to
  an advisory and/or component. The decision records both standing violations
  and applied exemptions, rendered as a table or JSON. `gate` exits `1` on
  violation, `0` on pass, `3` on unreadable input.
- Shared CLI scan pipeline: the extraction -> facts -> identification ->
  advisory-correlation work is factored into one module used by both `scan` and
  `gate`, so the two commands cannot drift.
- CycloneDX 1.6 VEX generation (`cudabom-sbom`) and the `cudabom vex` command:
  emits an SBOM of the identified components plus a `vulnerabilities` array that
  maps advisory verdicts to CycloneDX `analysis.state` (`affected` ->
  `exploitable`, `not_affected` -> `not_affected`, `under_investigation` ->
  `in_triage`), with each statement's `affects` pointing at the component's
  bom-ref. Verdicts with no matching component are still emitted (never silently
  dropped). Deterministic and reproducible.
- SBOM enrichment (`cudabom-sbom::enrich`) and the `cudabom enrich` command:
  merges discovered CUDA components into an existing CycloneDX document. The
  input is parsed as generic JSON so fields cudabom does not model are preserved
  exactly; duplicates (by purl or name+version) are skipped; cudabom is recorded
  in `metadata.tools.components` (leaving the deprecated array-of-tools shape
  untouched rather than corrupting it).
- Wired the previously-stubbed `vex` and `enrich` commands; `explain` and `db`
  remain declared for later.
- `cudabom explain [--id <finding-id>] <target>...`: scans and prints the full
  evidence chain behind a single finding (kind, detail, location, sha256/layer,
  conflicts) as text or JSON, with a short note on what the confidence level
  means. Without `--id`, lists every finding with its id. An unknown id is a
  usage error that lists the available ids.
- CSAF 2.0 ingestion (`cudabom-advisory`): parses NVIDIA CSAF bulletins
  (`product_tree` full-product-names and version branches, `vulnerabilities`
  with `product_status`) into the normalized advisory index, resolving products
  to cudabom components through a reviewed product map. Unmapped products are
  reported, never guessed or silently dropped.
- Product map (`cudabom-advisory::ProductMap`, `advisories/product-map.json`):
  case- and whitespace-insensitive exact and substring rules mapping CSAF
  product names to cudabom component names.
- `cudabom db build|status|update`: `db build` ingests local CSAF documents
  (a file or a directory of `*.json`) into a normalized index consumable by
  `scan`/`gate`/`vex --advisories`; `db status` reports mapped vs unmapped
  products; `db update` fetches NVIDIA CSAF from upstream. Because NVIDIA
  publishes no CSAF discovery manifest (`provider-metadata.json` / ROLIE feed),
  `db update` synthesizes one from the repository tree: the default `manifest`
  mode lists CSAF documents via the Git Trees API at a pinned commit and fetches
  only those files (verifying each against its published `.sha256` sibling), and
  a `tarball` mode downloads and unpacks the whole-repository archive as an
  air-gap / mirror fallback. CSAF documents are recognized by the
  `<year>/<id>/<id>.json` path convention, so `CVE-*.json` records and markdown
  siblings are ignored. Both modes feed the same offline ingestion path.
- Nightly advisory refresh (`.github/workflows/advisory-refresh.yml`): resolves
  NVIDIA's newest upstream commit, rebuilds the vendored `advisories/index.json`
  via `db update` pinned to that SHA, and opens a review pull request when the
  index changes. Scans read the committed, reviewed snapshot offline.
- Fingerprint database from NVIDIA redist manifests (`cudabom-identify`):
  `redist` parses NVIDIA's signed `redistrib_<version>.json` manifests
  (exact version <-> archive sha256 ground truth); `derive` turns them into
  `FingerprintDb` entries via a reviewed component-profile table (manifest key
  -> canonical component + SONAME stems), reporting unmapped keys rather than
  guessing. Derived data is sharded one file per upstream manifest under
  `fingerprints/cuda/`, merged at scan time by `FingerprintDb::from_dir` (which
  records hash/version collisions in a `MergeReport`). `cargo xtask fingerprints
  build` performs the derivation, and committed shards are regression-tested
  against real NVIDIA checksums.
- Shared network layer (`cudabom-fetch`): a single verified-download primitive
  with a conservative retry policy (5 attempts, 500ms base, exponential backoff,
  full jitter, 30s cap), rate-limit awareness (honors HTTP 429 and `Retry-After`
  in both delta-seconds and HTTP-date forms), retrying only transient failures
  (429/5xx/network) and never non-transient 4xx. `db update` was refactored onto
  it and exposes `--max-retries` / `--retry-base-ms` / `--no-retry`.
- Binary fingerprint layer (`cudabom-identify::binary`): derives GNU build-id and
  per-file sha256 from real unpacked `.so` bytes (via `cudabom-elf`), attributed
  by caller-supplied provenance, to identify individual shared objects (not just
  archives).
- Fingerprint corpus (`cudabom-identify::corpus` + `cargo xtask corpus`): a
  committed, reviewable `corpus.lock.json` (component/version/platform/url/sha256,
  digests from NVIDIA's manifest) drives `corpus fetch`, which verifies each
  download via `cudabom-fetch` into the gitignored `corpus/` tree; `fingerprints
  build --corpus` unpacks those archives (system `tar`) and folds binary signals
  into the shards. Binary attribution is gated by a reviewed SONAME allowlist
  (`soname_stems_for`), so libraries NVIDIA bundles but that are not part of a
  component (e.g. the `libcuda.so` driver stub and `libOpenCL.so` in the cudart
  archive) are never credited to it. The committed `redistrib_11.4.2.json` shard
  carries the real `libcudart.so.11.4.108` GNU build-id and file hash derived
  from the archive whose digest matches NVIDIA's signed manifest.
- Subset-first corpus controls: `corpus lock --limit N` caps the lockfile to the
  first N entries for a fast smoke run, and `corpus fetch --dry-run` prints the
  full fetch plan (per-entry `would fetch` / `present`) without touching the
  network or disk, so the pipeline is verified on a small sample before a full
  download.
- GPU capability manifest (`cudabom-fatbin::CapabilityManifest`): aggregates the
  SM (streaming-multiprocessor) architectures targeted by an artifact's device
  code across every fatbin entry, embedded fatbin, cubin, and PTX `.target`,
  separating compiled `cubin` targets from forward-compatible `ptx` targets.
  Surfaced in `scan` output (JSON `capability`, and a `gpu-capability:` block in
  the table view).
- Expanded the reviewed component profile table with additional CUDA
  redistributable libraries (`nvjitlink`/`libnvJitLink.so`,
  `cufile`/`libcufile.so`, `nvfatbin`/`libnvfatbin.so`, `nvrtc-builtins`) and
  no-shared-library tools (`cuobjdump`, `cuxxfilt`), keeping every SONAME stem a
  documented fact rather than a guess.
- Per-binary composition view: `scan` now reports a `composition` section
  separating, for each scanned file, the CUDA components it *links* (dynamic
  `NEEDED` dependencies) from those it *contains* (embedded/vendored or
  statically-linked copies), each node tracing back to its finding id. Derived
  purely from existing findings (no new parsing), so it never disagrees with the
  findings list. Rendered in JSON and the table view; CycloneDX components gain a
  `sourceFile` property tracing each to its originating binary.
- `docs/sources.md`: recorded the NVIDIA authoritative data-source hierarchy
  (redistrib manifests canonical for the fingerprint corpus; package repos, Repo
  Channels/CDN, Product Security CSAF, and NGC as scoped secondary feeds).
- CUDA 12.4.1 coverage: committed `fixtures/redist/redistrib_12.4.1.json` (the
  real NVIDIA manifest), the derived shard `fingerprints/cuda/redistrib_12.4.1.json`,
  and the reviewable per-release fetch plan `fingerprints/corpus.12.4.1.lock.json`.
  All 14 profiled components are fully binary-derived from their fetched-and-
  verified archives: 50 real GNU build-ids and 118 file hashes across cublas,
  cudart, cufft, cufile, curand, cusolver, cusparse, npp, nvfatbin, nvjitlink,
  nvjpeg, nvrtc (plus archive-hash records for the no-shared-library tools
  cuobjdump, cuxxfilt). Each component carries its own upstream version track
  (e.g. npp `12.2.5.30`, cublas `12.4.5.8`, cufile `1.9.1.3`), and the SONAME
  allowlist excluded bundled non-component libraries.

- CSAF ingestion now handles the real NVIDIA product-tree shape, where the
  `product_name` branch and its `product_version` branches live in sibling
  subtrees linked only by a product-id prefix, and the version text sits in the
  leaf product name (e.g. `v10.16.1`, `All versions prior to v10.16.1`). Product
  names are re-linked by product-id prefix, version descriptors are parsed into
  proper ranges (`v` prefix stripped, "prior to" phrasing bounded), and weak
  grouping labels (`NVIDIA`, `All`) no longer shadow the real product.
- `cudabom db update` no longer aborts when an upstream `.sha256` sidecar is
  stale: the offending CSAF document is skipped and reported (the pinned commit
  SHA remains the primary integrity anchor). Added `fetch_file_checked` /
  `FileOutcome` and an `Ingest::integrity_skipped` list surfaced on stderr.
- Raised MSRV from 1.82 to 1.85 for the `object` binary-parsing crate.

### Fixed

- **Scanner no longer panics on an empty file (e.g. a wheel's `__init__.py`).**
  The embedded-ELF scan (`find_embedded_elf`) begins searching at offset 1 and
  sliced `data[1..]` unconditionally, so a zero-length buffer, exactly what the
  empty `__init__.py` present in essentially every Python wheel produces when
  every walked file is scanned, panicked with `range start index 1 out of range
  for slice of length 0`, aborting the whole scan. A scanner fed untrusted input
  must never crash on a degenerate buffer; `find_embedded_elf` now returns no
  hits for any buffer at or below the ELF-magic length. Caught by scanning the
  real `nvidia-cudnn-cu12` wheel; covered by a regression test over empty and
  sub-magic buffers.

- **The distribution eval no longer penalizes cudabom for being more precise.**
  The eval's version consistency check treated a derived version that *extends*
  the ground truth as a mismatch (`cutensor 2.8.1.0` vs a wheel advertising
  `2.8.1`). It now accepts either direction of dotted-prefix overlap, so a more
  precise binary version grades as consistent rather than a false mismatch.

- **Streaming eval reclaims skipped artifacts.** In `--stream` mode, an artifact
  that was acquired but then skipped (e.g. a wheel with no bundled CUDA
  libraries, like `tensorflow`/`torch`/`jax` whose CUDA arrives via dependency
  wheels) bailed before the success-path cleanup, leaking its unpacked tree
  (~4 GB across three wheels in one run). The skip path now reclaims the working
  directory too, keeping peak disk at one artifact as intended.

- **A verbosity test no longer flakes under parallel execution.** Two tests
  mutated the process-global verbosity `LEVEL` and could race in the shared test
  binary; they now serialize on a test-local mutex.

- **The in-the-wild distribution eval net was widened across new failure
  modes.** Building on the initial harness, `eval/distribution.manifest.json` now
  also covers: **fat ML containers** (`pytorch/pytorch`, `tensorflow/tensorflow`:
  CUDA arrives via vendored pip wheels inside the image, a harder case than
  the clean `nvidia/cuda` base), a **Windows DLL** path (a renamed
  `cudart64_12.dll`), a **version spread** (CUDA 11.8.89 old wheel), a **non-x86
  platform** (aarch64 wheel), and three new adversarial `synthetic` transforms
  driven by a `transform` field: **`static-exe`** (link `libcudart_static.a`
  into an executable with no `.so`; falls back to the archive's member-hash path
  when a cross-toolchain is absent), **`upx`** (UPX-pack; skips honestly rather
  than mislabel if the packer refuses the foreign-platform binary on the host),
  and **`embed`** (library concatenated at a non-zero offset inside a larger
  blob). The report also surfaces a **GPU-code (fatbin/PTX) capability** column:
  distinct SM cubin targets cudabom extracts from embedded device code, a signal
  no general SBOM/CVE tool reports.

  Measured over the then-current artifact set (one container skipped on a disk
  limit, since fixed): cudabom named CUDA in all but one, pinned several
  exactly (including a
  stripped+renamed `libplugin.so`, a renamed Windows `plugin.dll`, a static-only
  `libcudart_static.a`, and a CUDA 11.8.89 wheel), returned a consistent major
  family for 5 (wheels shipping only `libcudart.so.12` etc.), and saw embedded
  GPU code in 6, versus Syft naming 4, blint 12 (name-only, no version/CVE),
  and Trivy correlating CVEs in 3 (its container strength). The honest negatives
  are recorded too: `embed` (library hidden at an offset) was a MISS at the time
  of this measurement (since resolved: see the embedded-ELF entry above), and the
  `upx` entry skips when packing is not possible on the host.

  eval measured cudabom on NVIDIA's pristine redist tarballs, its home turf.
  The distribution eval casts a wider net over the forms CUDA actually ships to
  users, so the competitor comparison is representative rather than stacked:
  **PyPI wheels** (official `nvidia-*-cu12` and third-party `cupy` wheels that
  *vendor and rename* CUDA libraries with no metadata of their own), **conda
  packages** (`.conda` = zip of zstd tarballs), **container images** (pulled by
  digest and exported), and **synthetic adversarial copies** (a real library
  stripped and renamed to defeat name/soname heuristics; only a content hash
  or build-id survives). A new `eval/distribution.manifest.json` content-pins every
  artifact (sha256 for downloads, image digest for containers) so the run is
  reproducible; downloads land in the gitignored `corpus/distribution` and nothing large
  is committed. For a fair comparison, Syft and Trivy run on the *native*
  artifact (the wheel/image, where their package metadata lives) while cudabom
  and blint run on the CUDA libraries found inside; container scans are focused
  to CUDA library names so a 4 GB OS rootfs is not swept in. Scoring is
  detect-plus-known: `exact` where the exact bytes are fingerprinted,
  `family-match` where only the SONAME-major library ships (e.g.
  `libcudart.so.12` → `12.x`), `detected` where no version ground truth exists,
  else `version-mismatch`/`miss`. The measured run showed cudabom
  naming CUDA in every scored artifact, including a stripped+renamed
  `libplugin.so` pinned to
  `cudart 12.4.99` exactly where Syft and Trivy name nothing, and 14 CUDA
  components enumerated inside the `nvidia/cuda` container.

- **The fingerprint-DB loader no longer mis-reads non-shard JSON.** The
  recursive multi-tree loader (`FingerprintDb::from_dir`) previously tried to
  parse *every* `*.json` under the database directory, which failed on the
  `corpus.*.lock.json` provenance locks that sit beside the per-product shard
  directories. It now accepts only `redistrib_*.json` shards (regression test
  added), so `--db fingerprints` loads the whole tree cleanly. The eval harness
  `--db` default now points at the `fingerprints` parent so every product shard
  tree is loaded.

- **Sibling CUDA-X redistributable trees are now discovered and fingerprinted.**
  Discovery previously covered only the CUDA toolkit tree
  (`compute/cuda/redist/`). It now iterates NVIDIA's full documented set of
  redistributable products (CUDA Installation Guide, "Available Tarball and Zip
  Archives"): **cuDNN, NCCL, cuTENSOR, cuDSS, cuSPARSELt, cuQuantum, nvJPEG2000,
  nvTIFF, cuBLASMp, NVPL, and NVSHMEM**, each from its own
  `compute/<product>/redist/` channel. The product *set* is a one-line
  declarative table (`REDIST_PRODUCTS`); every product's *versions* and
  *components* stay fully dynamic. `cargo xtask corpus discover` gains
  `--product <name>|all` (default: all); shards and fixtures are kept per product
  (`fingerprints/<product>/`, `fixtures/redist/<product>/`), and the fingerprint
  DB loader, corpus-lock loader, bundler, and `cudabom update` unpacker all read
  the tree recursively. Component profiles with SONAME stems, verified from the
  real archives, were added for every new library (e.g. cuDNN's split
  sub-libraries `libcudnn_adv/cnn/ops/graph/...`, NVPL's eight packages), so a
  scanned sibling `.so` identifies exactly instead of missing.

  Two manifest-schema differences were handled to make this correct:
  - **CUDA-variant nesting**: cuDNN/cuTENSOR/cuDSS/nvSHMEM/… nest archives one
    level deeper under a `cuda12`/`cuda13` variant key. The manifest parser now
    reads both the flat (CUDA toolkit, NVPL) and variant-nested shapes, keying
    variants as `linux-x86_64-cuda12`; the platform filter matches a requested
    `linux-x86_64` against all its variants.
  - **NCCL's CUDA-qualified labels**: NCCL names manifests
    `redistrib_<ver>-cuda<X.Y>.json`. Discovery and version-ordering now accept
    and preserve that qualifier.

- **`advisories/product-map.json` is now generated from the component profiles,
  not hand-maintained.** The CSAF product → component substring rules were a
  second list that could silently drift from the fingerprint component profiles.
  Each `ComponentProfile` in `crates/cudabom-identify/src/derive.rs` now carries
  an `advisory_terms` field, and a new `cargo xtask product-map` task renders the
  map from those terms plus a small reviewed seed (`MANUAL_RULES`) for umbrella
  and unprofiled products (`cuda-toolkit`, `cuda-driver`, `tensorrt`). Adding a
  component in one place now updates fingerprint attribution *and* advisory
  matching together, including every new sibling tree above. The generator also
  orders more-specific substrings first (so `nvjpeg2000` is not shadowed by
  `nvjpeg`).
  - `cargo xtask product-map --check` (CI `hygiene` job + a pre-commit hook +
    a unit test) fails if the committed file drifts from the profiles.
  - `cargo xtask product-map --write` regenerates it; the nightly
    `fingerprint-refresh` workflow runs `--write` and includes the result in the
    same review PR as new shards, so the map stays current with no manual step.

- **Four previously-missed CUDA shared-library components are now identified.**
  The reviewed component-profile table covered ~16 of the ~61 redist component
  keys; several unmapped keys ship real shared libraries that scanned to nothing.
  Added profiles (with SONAME stems verified from the archives) for **CUPTI**
  (`cuda_cupti` -> `libcupti.so`, `libnvperf_host.so`, `libnvperf_target.so`,
  `libcheckpoint.so`, `libpcsamplingutil.so`), **NVVM** (`libnvvm` ->
  `libnvvm.so`), **cuDLA** (`libcudla` -> `libcudla.so`), and **cuobjclient**
  (`libcuobjclient` -> `libcuobjclient.so`), plus product-map rules so direct
  advisories for them correlate. A scanned `libcupti.so` now identifies as
  `cupti <ver> (exact)` with toolkit-wide CVEs correlated, where before it was a
  complete miss.

- **Build-time guard against silently missing a new CUDA library.** When a
  corpus is present, `fingerprints build` now inspects every unmapped manifest
  key's archive and, if it ships a `.so`, emits a loud WARNING naming the key and
  stems to add. Compilers/headers/datacenter tools (which ship no `.so`) stay
  quiet. This is the automatic tripwire so a future NVIDIA library addition
  cannot slip through unattributed.

- **Windows DLLs are fingerprinted by hash (exact versions).** The binary layer
  previously processed only `.so` files, so a Windows CUDA DLL fell back to its
  PE version resource, which does not always carry the full micro version (e.g.
  `cublas64_11.dll` stamps only `11.11.3`, not the archive's `11.11.3.6`).
  `fingerprints build` now also extracts `.zip` archives and records each owned
  DLL's SHA-256, so the hash path recovers the exact version. `cublas64_11.dll`
  now identifies as `cublas 11.11.3.6 (exact)` instead of `11.11.3 (likely)`.

- **Early CUDA toolkit CVEs never fired (missing release label).** NVIDIA's
  `redistrib_*.json` manifests only began carrying an explicit `release_label`
  field in CUDA 12.2; the 24 earlier manifests (11.0.3 through 12.1.1) omit it.
  Because toolkit-wide advisories are correlated to a scanned library *through*
  the CUDA release that shipped it (`release_label` -> `release_versions`), the
  absence meant that **none of the toolkit CVEs correlated for the oldest, often
  most-vulnerable toolkit versions**: e.g. a scan of `cudart 11.8.89` reported
  "no advisory affects" despite 26 applicable toolkit CVEs. `fingerprints build`
  now backfills the release label from the manifest filename
  (`redistrib_11.8.0.json` -> `11.8.0`, NVIDIA's own release directory label)
  when the manifest itself is silent. After rebuild, `cudart 11.8.89` surfaces
  26 toolkit-wide CVEs (4 high, 19 medium, 3 low), honestly labeled "shipped in
  CUDA 11.8.0; keyed to the toolkit, not necessarily this file."

- **Embedded fatbin detection missed every real binary (byte-reversed magic).**
  The fatbin wrapper magic constant was stored byte-reversed
  (`0x50ED55BA` instead of the documented `0xBA55ED50`), so the scan for the
  on-disk byte sequence `50 ED 55 BA` matched nothing in real libraries. As a
  result, `scan` reported `embedded_fatbins: 0` and an empty GPU capability for
  binaries that embed CUDA code (e.g. a PyTorch `libtorch_cuda.so` with 256+
  fatbins across `sm_50..sm_90`). The existing fixtures used the magic constant
  symbolically, so they could not catch the reversal. Fixed the constant,
  corrected the standalone-fatbin CLI fixture (which hardcoded the reversed
  bytes), and added a regression test asserting the literal on-disk byte order
  (`50 ED 55 BA`). Real `libtorch_cuda.so` now reports 256 GPU code units with
  `cubin_sm_targets [50, 60, 70, 75, 80, 86, 90]`.

### Known limitation

- **CUDA 11.0.3-11.4.1 have no fingerprintable corpus, by NVIDIA's own data.**
  These releases were flagged as "manifest-only shards that could be back-filled",
  but their `redistrib_*.json` (both our fixtures and NVIDIA's upstream) contain
  **only** datacenter components (`fabricmanager`, `libnvidia_nscq`): zero CUDA
  toolkit libraries. NVIDIA did not publish the full-toolkit redist (cudart,
  cublas, cufft, …) until **11.4.2**. There is nothing to lock, fetch, or
  fingerprint for the earlier releases, so they correctly have no corpus lock;
  this is a boundary of the upstream data, not a cudabom omission.
